# Strata 多对话缓存方案（M4 设计，尚未实现）

2026-09-29。以已部署 M3 为基础；本轮只核对本地源码和设备，没有改动引擎、配置或 ZCode，也没有中断现有服务。

## 建议

保留一份活动 GPU 状态，SSD 保存两份不活动对话快照，模型权重和 prefill 工作缓冲始终共享。建议先使用 G:\Strata-cache\conversations，磁盘预算 16 GiB，传输暂存使用两个 64 MiB 缓冲区，总计约 128 MiB，另加少量元数据。

本机 D 是 BIWIN X570 PRO，G 是 Fanxiang S790，两者属于不同物理 SSD；模型和 ngram 位于 D。选择 G 是为了减少和 D 盘 ngram I/O 争用，不代表已经实测 G 的快照吞吐更快。两盘目前均有数百 GB 可用空间。

不建议再启动一份模型进程，也不建议把所有不活动 KV 常驻 RAM。M3 测试时最低可用 RAM 约 2.83 GiB，多套长对话常驻 RAM 会很快吃完余量。

## 现有缓存为什么不够

`src/program/generate.cpp` 的 `ConvCheckpoint` 只保存 token/图片标识、GDN 递归状态、PLE 历史和 QSA 索引尾部。已有检查点约 118056960 字节/份，不包含完整 KV 和已完成的索引池。

`checks` 中所有检查点共享当前唯一一份 KV 历史。serve 在确定 resume 后会删除不属于当前前缀的检查点，再重写后面的 KV。所以增加 `--prompt-cache` 数量只能增加同一条历史上的回退点，不能保住被另一条对话覆盖的分支。

ZCode 的 project_memory_extract 调用了同一模型，形成另一条提示词分支。这是本次优先解决的“主对话 A → 后台任务 B → 主对话 A”场景，不要求 ZCode 新增会话 ID。

## 必须保存和恢复的内容

| 状态 | 来源及处理 |
|---|---|
| 有效 token、有效长度、图片标识 | 保留 `live` 和每个检查点的 ids/imgs；有效长度取引擎已提交长度，不能用客户端收到的输出长度代替 |
| 主模型 12 层 QSA KV | INT8 K/V 加 FP16 scales；按实际使用的页数保存，不复制整个 262K 容量 |
| QSA 索引 | 已完成 pooled 行、尾部、边界/备用行及必要计数；边界须覆盖未满 4-token 页的情况 |
| GDN 递归状态 | 所有层完整状态，无法靠 KV 或 token 数恢复 |
| PLE/ngram 状态 | 卷积历史及前序 token；不复制 SSD 上的 ngram 权重表，行缓存可继续共享 |
| MTP 草稿 KV | `MtpDrafter::kv_state()`；当前环形 GPU 缓冲背后的 host KV 是权威副本。初版保存有效历史对应的 host 范围，恢复后调用 ring restore |
| 回退检查点 | 保存当前保留的检查点，最多沿用现有 6 份；MTP 要能够支持这些位置的回退，不能只存最新 32K 环形窗口 |
| 兼容标识 | 当前运行实例、模型/量化/几何、KV 格式、控制向量状态、快照格式版本 |

不保存模型权重、专家缓存内容、RoPE 常量表或临时 GEMM 缓冲。专家 cache 及其 d_res 映射全局共享，不能仅恢复旧映射而不恢复相应权重槽。每次请求已重新建立 suffix draft 和 penalty history，这些应保持现有重建方式。

CUDA graph 捕获了内存地址，恢复必须复制到原来的状态缓冲区，不能更换指针。图片的 MRoPE 位置表继续按新请求构造，不能用旧快照的位置表覆盖新请求的图片布局；匹配时需确认恢复前缀内的图片内容和网格一致。

第一版建议明确只支持当前生产配置：INT8 KV、主模型 KV 全显存、MTP ring/host 模式。对其他 KV 格式或主模型 streaming 模式明确禁用此功能，不误用格式。后续可扩展到按 host 权威副本恢复、重置 residency map 的 streaming 方案。

## 大小估算

按当前模型：单层 INT8 KV 为每 token 1056 字节，主模型 12 层，MTP 额外 1 层。主模型 pooled index 约每 token 1536 字节。当前 live 的递归状态加每份历史检查点各约 118 MB。

下表假设保留 2–6 份历史检查点，另有一份 live 状态，并完整保存 MTP 有效历史；不含少量元数据、对齐及临时文件开销。是源码布局估算，尚未实际序列化测量。

| 对话有效长度 | 每套不活动快照约占 SSD |
|---|---:|
| 32K | 0.80–1.24 GiB |
| 64K | 1.26–1.70 GiB |
| 128K | 2.19–2.63 GiB |
| 256K | 4.06–4.50 GiB |

这比 M3 报告中只统计主模型 KV/索引和一份递归状态的数字更完整。不能把“检查点约 118 MB”当作一套独立对话的总成本。

16 GiB 预算足以容纳两份 256K 不活动快照，并为替换写入留下空间；预算必须连同临时文件一起计算，不能只限制已经提交的文件。

## 匹配与切换流程

1. 新请求入队后，先比较当前 live、当前检查点，以及 SSD 快照索引中所有有效恢复点。按完整 token 前缀、图片标识和兼容条件寻找匹配；摘要只加速筛选，最终仍验证前缀。
2. 保留现有正常续聊快路径。当前活动状态能继续时，不读写 SSD。相同恢复长度优先活动状态；只有离线状态能够显著减少重算时才考虑恢复，避免为很短的相同 system 前缀支付大额 I/O。
3. 当请求将切换历史分支、覆盖有价值的旧分支时，在现有 `checks.erase` / `session_zero` 之前保存旧状态。保存时同步相关 GPU 工作并处理 pending expert swaps，使复制期间序列状态不再变化。
4. 写入只覆盖有效页、状态与检查点。使用固定大小暂存分块搬运，临时文件写完并校验后才提交。初版不压缩，不为每次同对话续聊重复写全量快照。
5. 若匹配离线快照，将其恢复到原 GPU/host 地址，再选择该快照中与本次请求匹配的 live 或检查点恢复点。补读的仅是匹配点之后的新 token。
6. 切换后由 LRU 管理两份不活动快照。文件数量和总字节双重限制。新增快照失败不破坏当前有效状态；恢复失败后清零并重新 prefill，不能继续使用部分恢复的数据。

示例：A 已读 60K → B 后台记忆请求到来 → 保存 A → 执行 B → A 续聊到来 → 保存 B（符合保留策略时）→ 恢复 A → 只读新增部分。B 的首次读取仍然需要 prefill；多缓存省去的是返回 A 时的重复读取。

分支判定不能仅用 `resume == 0`：两个任务可能共享同一个 system 前缀。应结合上一请求的末轮边界检查点，识别即将丢弃的大段历史。另一方面，正常续聊因聊天模板重排而退回最近 turn checkpoint 时，不应每轮都另存一套。建议记录上一次 turn boundary 和分支版本，把正常末尾重算与切换到较早分支区分开。

## I/O 与失败处理

- Windows 优先用对齐的顺序、非缓冲文件 I/O，避免把数 GiB 快照塞进系统文件缓存；实际对齐由设备信息决定。不要用整文件 mmap 维持所有离线快照在内存中。
- 两个 64 MiB 暂存缓冲可让复制与写盘分块流水，但旧 GPU 状态在相应数据转移完成前必须保持不变。第一版应先保证正确性，不承诺后台无阻塞切换。
- 主线程只在请求边界切换，不在生成中途换上下文。用户取消、图片变更、控制向量变更均走明确分支。
- 被取消的半次 prefill 不能把旧 `live` 向量误当作当前 KV 的有效历史。第一版优先保存完整完成的会话；取消的分支只使用明确有效的检查点，必要时丢弃该分支。
- 快照内容分段校验，检查长度、偏移、版本及范围；写满、截断、恢复中途失败均退回正常 prefill，不输出基于混合状态的答案。
- 第一版仅在本次引擎启动期间复用，缓存目录按运行实例隔离。跨重启复用需要更严格的模型/构建指纹和格式兼容设计，另行实现。
- 记录 save_ms、restore_ms、bytes、resume_tokens、命中来源和 miss 原因；快照恢复时间与真正新增 token 的 prefill 时间分开显示，避免把磁盘恢复冒充推理吞吐。

尚未进行实际 GPU↔SSD 快照测速，不能承诺固定 1 秒内恢复。收益取决于完整保存与恢复成本，而不只是 SSD 顺序读取速度；验收应对比 A→B→A 的总耗时。M3 已把 60K 重读缩短至约 33 秒，这应作为本机比较基线。

## 实施与验收

建议新建独立 conversation snapshot 模块处理布局、文件格式与流式 I/O；在 MTP 添加受控导入/导出接口；serve loop 只负责分支选择、快照生命周期和恢复入口，避免继续把所有逻辑塞进 generate.cpp。

拟议配置（尚未存在的参数）：`--conversation-cache-dir`、`--conversation-cache-slots 2`（不活动快照数量）、`--conversation-cache-max-gib 16`。现有 `--prompt-cache 6` 继续表示单条历史上的检查点数量，含义保持不变。

验收至少覆盖：

1. 固定专家分配与 PCIe 分流设置下，对照 A 连续续聊与 A→B→A，恢复后逐部分 STATE_HASH 与首个 verify 窗口 logits 一致，再比较输出 token；不能只凭“答案看起来正常”。
2. 分别检查 KV、scales、pooled index、GDN、PLE、MTP 和有效长度，覆盖长度不整除 4、回退到较早 checkpoint、拒绝草稿后切换的边界。
3. 32K、64K、128K 及最终 262K 的长短对话混切；默认动态专家替换、图片前缀相同/不同、控制向量开关都不误命中。
4. 取消、重试、磁盘不足、截断快照、超限淘汰和恢复失败后的重读路径。保持单活动推理序列；现有入口实际用 threading.Lock 串行化，并不保证严格 FIFO。需要可预测顺序时应增加显式队列，不引入并行运行两条 GPU 推理序列。
5. ZCode 主对话→项目记忆提取→主对话的真实链路，记录总等待时间、保存/恢复耗时、重读 token 数、磁盘流量、峰值 RAM/VRAM。
6. 同一对话正常连续使用时不频繁写 SSD，M3 的 prefill 吞吐和内存余量不明显回退。

结论：建议实现受限的 SSD 多会话快照，优先覆盖主对话被后台任务打断的场景。它是明确可行的引擎功能扩展，不是改一个缓存数量参数即可完成；当前没有部署此功能。

## 活动缓存、并发和 CPU 分工补充

“活动”表示当前正在被唯一一条推理执行路径读取和更新的对话状态：主模型 KV/递归状态等主要位于 GPU，MTP 还带 host 历史。它不表示其他对话被删除。不活动快照只是已经计算好的状态暂存在 SSD，恢复后才能继续执行，不会自行生成 token。

当前 HTTP 服务用 ThreadingHTTPServer 接收多个连接，Service.run 的 threading.Lock 将实际模型调用串行化。请求准备还有一部分发生在锁外。多缓存能减少轮到另一条历史时的重算，但不会让三套状态同时执行，也不会令算力或吞吐变成三倍。

要承受突发并发，应单独增加有界请求队列、准入控制、排队超时、断开取消和明确的繁忙响应；限制应尽可能在昂贵的请求准备之前执行。可从 2–4 个排队请求起步压测，这只是拟议上限，不是已经验证的并发能力。长期到达速度高于处理速度时，任何有限队列都会饱和。

主请求优先需要可靠的请求分类（客户端标识或可验证的任务信息），不能盲目猜测所有短请求都是后台任务。优先级只决定下一条执行顺序，不能立刻抢占已经开始的后台长请求。真正改善这种阻塞还需要 prefill 分块调度/生成边界暂停，或者多序列连续批处理；这超出 SSD 多快照的第一版范围。

本机 CPU 为 Ryzen 9 9950X3D，16 核 32 线程。现有引擎已用 15 个专家 worker 加参与工作的主线程，并将它们绑定到物理核心；专家 cache 未命中的计算在 CPU 与通过 PCIe 交给 GPU 的路径间分配，当前默认 pcie_frac 0.55 不是整个模型的 GPU 工作占比。批量 prefill 主要依赖 GPU，CPU 还承担调度、准备和 I/O。

可以实测调整 --pool-workers、核心绑定和 --pcie-frac，并让快照校验/文件 I/O 使用受限后台线程与数据复制重叠。CPU 专家计算也受内存带宽限制，使用全部 32 个逻辑线程或一味增加 CPU 分担不保证更快。实际优化指标应是请求延迟、总 token 吞吐和内存占用，而不是任务管理器 CPU 占用率。

不建议为了并发让 CPU 独立再跑当前完整模型：剩余 RAM 不适合再放一套权重，而且当前 7000 个专家的唯一副本位于 GPU，现有 CPU 路径不能直接脱离 GPU 执行整套模型。共享权重的异构多序列调度在架构上可以研究，但仍需多套序列状态和独立调度，不能由现有多快照功能自动获得。

## 类似 vLLM 的共享缓存池：更长期的目标架构

可以实现。2026-09-29 对照 vLLM 官方 [前缀缓存设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)：KV 以块为单位管理，前缀链和当前 token 等共同参与块的哈希，物理块记录使用它的请求引用计数。相同有效前缀可以指向同一份缓存。vLLM 的 [混合缓存管理设计](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager/) 也区分不同类型的状态并协调命中位置；这不等于其实现可直接接入本地这个定制模型。

Strata 已有每层 QSA 页表，4-token 物理页，部分读取和写入经页表寻址，并有 CPU/GPU KV streaming 的映射机制。这是实现共享池的基础，但当前是单历史缓存，尚无多会话所有权、跨会话引用计数及写时复制。部分 prefill staging 采用 identity layout，session_zero 会清空整个现有状态区域，这些路径必须一起审查，不能只添加一个全局哈希表。

共享池有两层收益：

1. **容量共享**：将给单条对话预留的 262K KV 容量改为全局预算，多会话按实际 token 数占用。即使前缀不同，四条 32K 历史的主要 KV 数据也约相当于 128K token；还要额外计算各会话的递归/索引状态等。262K 是池的总预算时，不代表每个并发会话都能无代价占用 262K。
2. **内容共享**：完全相同的前缀只保存一次。例如两条历史各含同一份 30K 前缀和各自 10K 后缀，主体 KV 可从 80K token 份缩到约 50K token 份，另加页边界和状态开销。相同资料出现在不同前文之后并不构成可安全复用的相同前缀。

建议将 KV/pooled-index 块池与 GDN/PLE/MTP 恢复状态分开管理：KV 小块可共用；递归状态只在有限的轮次边界/周期边界保留快照，按对应前缀归档。不能每 4 个 token 都保存一份约 118 MB 的递归状态。实际恢复位置必须同时满足 KV/索引和全部递归状态可用，KV 命中再长，也不能越过可恢复的状态边界。

写入共享的未完成尾页之前，需要私有页或写时复制；被请求引用的页不能被 LRU 直接淘汰。分支、MTP 草稿和 verifier 回滚都必须遵守同样的所有权规则。缓存键需要包含模型运行标识、位置/图片条件和控制向量条件等，不能只对本块 token 做独立哈希。

可选演进顺序：

1. 用完整快照验证所有状态的导出/恢复正确性，先处理 A→B→A。
2. 将快照拆为不可变共享块与按会话保存的状态；引入全局空闲页池、引用计数、私有尾页和页表切换。最初仍可一次执行一个请求，共享池本身不依赖连续批处理。
3. GPU 保留热块，SSD 保存冷块；RAM 只做受限暂存。按块换入换出与共享前缀可减少整套快照重复 I/O。常用工作集放得下时，不需要每次切换都访问 SSD。
4. 再扩展调度器和内核的序列维度，实现 chunked prefill、多会话分时执行或 continuous batching。不同会话的 token、位置、GDN/PLE 状态、MTP 窗口和采样参数必须隔离，不能把现有同一序列的多 token verify 当作多序列 batch。

如果目标扩展为多用户并发，共享块池比长期依赖整套 SSD 快照更合适；整套快照仍可作为先验证正确性、尽快减轻后台任务干扰的阶段。现阶段没有实施共享池，也没有据此宣称已具备某个并发数。
